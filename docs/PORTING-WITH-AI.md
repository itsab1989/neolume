# Porting playbook for AI coding agents

**For the human:** paste this one prompt into your AI coding agent (it needs access to a folder on your computer and a
terminal), replace the part in angle brackets, and answer its questions:

<!-- hand:prompt -->
```text
Read https://raw.githubusercontent.com/itsab1989/neolume/main/docs/PORTING-WITH-AI.md and follow it exactly to build
the app for my TV: <brand and model, e.g. "LG OLED C1">. Work in a new folder; ask me only for things you cannot do yourself.
```
<!-- /hand:prompt -->

The agent will ask you to do physical things (switch on developer mode, press buttons, look at the TV) and to approve
steps. At the end – and whenever it is unsure on the way – it walks you through the [acceptance test plan](TEST-PLAN.md)
with your remote, step by step; no technical knowledge needed. It must never ask for your passwords, Plex tokens or PINs in
the chat – if it does, say no.

## Prompts

A port takes many sessions. Besides the start prompt above, these four short prompts cover the usual moments – paste them
into the agent in the same port folder: **Continue** (new session), **Test** (with your remote), **Update** (new version of
the reference app) and **Share** (optional, when the port is done).

**Continue** – in a new session, or when the agent lost track:

```text
Continue the port of the app to my TV. Read PORTING-STATE.md and REQUIREMENTS.md in this folder, re-read
https://raw.githubusercontent.com/itsab1989/neolume/main/docs/PORTING-WITH-AI.md and carry on where the state file says.
```

**Test** (replace the part in angle brackets, or write "everything"):

```text
Walk me through the acceptance tests of the reference's TEST-PLAN.md for <feature, e.g. "the player">, one step at a time
in plain words. Translate the key names to my remote, record my answers in REQUIREMENTS.md and fix what fails.
```

**Update** – after a new version of the reference app:

```text
The reference app has a new version. Follow section 9 "Staying current" of the porting playbook: find what changed since
the spec version in PORTING-STATE.md, update the port, and walk me through the changed tests and the smoke test.
```

**Share** (only if you want others to find your port):

```text
Prepare the entry for my port in the reference's ports.json as described in section 8, step 6 of the porting playbook.
Show me the entry and the pull request text before you send anything.
```

## 1. Role and goal (agent, read this first)

You are the lead developer of a **port** of Neolume – an unofficial client for Plex Media Server – to the human's TV.
Goal: an app on that TV with the **same functions and look** as the reference app, adapted to the TV's control concept and
using the TV's advantages, that meets the reference's acceptance criteria and performance budgets.

Your sources of truth, in this order:

1. **The product specification** – [SPEC.md](SPEC.md). Every requirement has an ID (`NAV-5`, `PLAY-3` …), some have
   explicit *Accept:* criteria; numbers are marked measured [M] or target [T]; [?] marks unverified points – verify them
   on the target. Part B lists the old TV's workarounds and their modern replacements; Part C is the porting guide and the
   API contracts. Always refer to requirements **by ID** (in code comments, tests, commits and `REQUIREMENTS.md`).
2. **The acceptance test plan** – [TEST-PLAN.md](TEST-PLAN.md): one entry for every Part A requirement, either a test you
   walk the human through (written so you can read it out step by step) or a check you do yourself. It decides whether a
   feature is done.
3. **The design system** – `design/tokens.json` (every colour, type style, spacing, radius, focus, motion and layout value,
   each with a description and how it scales to 1080p/4K) and the icon SVGs in `design/icons/`. Take values from these
   files – never measure colours or sizes from screenshots.
4. **The reference screenshots** and the **visual-test scene list** – how each screen looks, and the list of screen states
   that must exist in the port.
5. **The UI text tables** – `src/i18n/strings.en.js` and `src/i18n/strings.de.js`. Reuse the texts as they are (same terms
   and button names, SPEC A15); the length limit of each key prefix is in `tools/i18n_rules.js`.
6. **The reference source code** – the reference repository (ES5 web app; pure logic modules in `src/core`, `src/plex`,
   `src/player` with Node unit tests in `tests/`). Read it when the spec is not precise enough; the code wins over your
   assumptions, the spec wins over the code's 2014-specific workarounds. Section 1.2 lists the parts you can reuse.

All of these are maintained together with the app and checked on every build of the reference, so they are current as long
as you read them from the `main` branch. **Re-read the relevant SPEC sections and test-plan entries at the start of every
phase** – they change with each release (version above).

### 1.2 Reusable parts of the reference implementation

Much of the reference is **platform-independent logic**: no DOM, no network calls of its own, unit-tested in Node. On a
web-based TV platform (Tizen, webOS, any browser engine) you can copy these modules with small changes; on a native
platform (Kotlin, Swift) port them line by line **together with their unit tests** – the tests are the quickest proof that
your port behaves the same. Every module is an ES5 function that attaches itself to one global namespace `N` (`N.util`,
`N.t` …). When you copy one, replace that with your module system and swap the dependencies the generated table names.

## 2. Ground rules

- **Ask the human only** for physical actions (switching on developer mode, pressing remote buttons, confirming what the
  TV shows, connecting cables), for consents (installing tools, changing TV settings, publishing) and for preferences.
  Find everything else out yourself (documentation, experiments, logs).
- **Never ask for or accept passwords, Plex tokens or PINs in the chat.** Sign-in happens on plex.tv in a browser or on the
  TV (SPEC A4, SEC-2, SEC-3). Tokens never go into logs, commits or messages. If a secret appears anywhere, tell the human
  to revoke it on plex.tv (*Authorized Devices*).
- **Local values** (TV and server addresses, developer certificates, keys) go into a git-ignored config file; add the
  `.gitignore` entry before the first commit.
- **Never** factory-reset the TV, change router settings, disable security features beyond the TV's official developer
  mode, or scan networks other than the human's own (and only with consent).
- **State file:** keep `PORTING-STATE.md` in the port repository: the spec version you build against (version line
  above), current phase, done/open requirement IDs, decisions with reasons, open questions for the human, measured
  numbers. Update it at the end of every work step so a new session can continue from it. Keep `REQUIREMENTS.md`: every requirement ID of SPEC.md with status (`done`, `partial`, `planned`,
  `n/a` + reason) and how it was verified.
- **Commit often** (small commits, message names the requirement IDs). Work in the phases below; a phase is finished only
  when its **exit criteria** are met and recorded in the state file.
- **Don't invent behaviour.** If SPEC.md and the reference disagree or something is unclear, note it in the state file,
  choose the reference behaviour, and tell the human.
- **Brand and policy:** no "Plex" in the app name or icon, no impersonation of official apps, no telemetry (SPEC A18). Use
  your own app name; keep the notice "unofficial client for Plex Media Server, not affiliated with Plex, Inc.".

## 3. Phase 0 – discover the target platform

Find out, by research and by asking the human to read things off the TV, and write the results to `PLATFORM.md`:

1. Exact model, OS name and version (the human reads it from the TV's About/Support page).
2. The official developer program and SDK/CLI for this OS; how to enable developer mode on this model; licence/account
   requirements; how long a developer install stays valid.
3. How apps are installed: store, sideloading, developer install; packaging format and signing.
4. Logging and debugging channels from the TV back to the computer (debugger, log stream, network log endpoint).
5. Remote key injection from the computer (needed for automated tests and the benchmark); if none exists, plan an in-app
   benchmark that presses keys itself (SPEC A17.3).
6. Runtime capabilities: UI resolution and density, app technology options (web, native), video/audio codecs and HDR
   formats the player decodes (to be confirmed at runtime in phase 1), subtitle rendering, TLS 1.2+ to plex.tv
   (→ decide: sign-in on the TV and direct plex.tv calls, **no helper** – SPEC B-1, C1), input devices (D-pad, colour keys,
   digits, pointer, touch surface, voice), background/screensaver APIs, secure storage.
7. If there is **no supported way** to install own apps: stop and tell the human; suggest an Android TV / Google TV device on
   the HDMI input instead and continue with that platform.

**Exit criteria:** `PLATFORM.md` answers all seven points with sources (links) or "verified on the TV"; the technology choice
and the install channel are agreed with the human.

## 7. Adaptation rules

- **Control concept:** map the reference keys (SPEC A3.2, A3.3) to the platform's remote. Every colour-key and digit

  remotes: implement NAV-2 including the damping rules of Part B (B-8). Use the platform's Back key for RETURN.
- **Platform advantages:** UI at 1080p/4K (SPEC A16.6); codec support from runtime capabilities in the client profile
  (PLAY-3, B-7); native text/ASS subtitle rendering (PLAY-11); request headers instead of tokens in URLs (SEC-3); secure
  storage for tokens; direct plex.tv sign-in and Discover/watchlist (B-1 – no setup program, no helper); voice/system search
  feeding Search (SRCH-1) where offered; gapless audio and playback speed where the player offers them (MUS-8).
- **Drop the 2014 workarounds** listed in Part B (B-1 … B-18) unless `PLATFORM.md` shows the same limitation on this TV;
  record each decision in the state file.
- **Keep the product rules:** cache-first start, per-profile settings, the "no work in the focus step" rules PERF-14 …
  PERF-16, texts within the limits of SPEC A15, PMS-only daily use (PRIN-12).

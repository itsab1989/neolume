# Porting playbook for AI coding agents

**For the human:** paste this one prompt into your AI coding agent (it needs access to a folder on your computer and a
terminal), replace the part in angle brackets, and answer its questions:

<!-- hand:prompt -->
```text
Read https://raw.githubusercontent.com/itsab1989/neolume/main/docs/PORTING-WITH-AI.md and follow it exactly to build
the app for my TV: <brand and model, e.g. "LG OLED C1">. Work in a new folder; ask me only for things you cannot do yourself.
```
<!-- /hand:prompt -->

The agent will ask you to do physical things (switch on developer mode, press buttons, look at the TV) and to approve
steps. At the end – and whenever it is unsure on the way – it walks you through the [acceptance test plan](TEST-PLAN.md)
with your remote, step by step; no technical knowledge needed. It must never ask for your passwords, Plex tokens or PINs in
the chat – if it does, say no.

**What you need:**

- an AI coding agent that may use a folder and a terminal on your computer (not just a chat window),
- your TV in its developer mode, on the same home network as the computer – the agent finds out how and tells you what to
  press,
- your Plex Media Server with a few movies or shows to test with (running Jellyfin or Emby instead? See
  [section 10](#10-using-another-media-server-jellyfinemby)),
- **a way for the agent to see the TV screen.** Best is the TV platform's own screenshot command, which the agent runs
  itself (Android TV, Google TV and Fire TV have one over the network; for other TVs the agent checks the developer
  tools). Otherwise a **camera pointed at the TV**: a webcam on the computer, an old phone with an IP-camera app or a
  network camera – on a stand, so it does not move and the agent can take a picture whenever it needs one. Without either,
  you describe the screen in words. That works, but it is much slower and mistakes slip through, because small
  differences (text slightly off, a wrong colour, a focus ring in the wrong place) are hard to put into words,
- time: a port is built over several sessions, and you can stop at any point and continue later.

## Prompts

A port takes many sessions. Besides the start prompt above, these four short prompts cover the usual moments – paste them
into the agent in the same port folder: **Continue** (new session), **Test** (with your remote), **Update** (new version of
the reference app) and **Share** (optional, when the port is done).

**Continue** – in a new session, or when the agent lost track:

```text
Continue the port of the app to my TV. Read PORTING-STATE.md and REQUIREMENTS.md in this folder, re-read
https://raw.githubusercontent.com/itsab1989/neolume/main/docs/PORTING-WITH-AI.md and carry on where the state file says.
```

**Test** (replace the part in angle brackets, or write "everything"):

```text
Walk me through the acceptance tests of the reference's TEST-PLAN.md for <feature, e.g. "the player">, one step at a time
in plain words. Translate the key names to my remote, record my answers in REQUIREMENTS.md and fix what fails.
```

**Update** – after a new version of the reference app:

```text
The reference app has a new version. Follow section 9 "Staying current" of the porting playbook: find what changed since
the spec version in PORTING-STATE.md, update the port, and walk me through the changed tests and the smoke test.
```

**Share** (only if you want others to find your port):

```text
Prepare the entry for my port in the reference's ports.json as described in section 8, step 6 of the porting playbook.
Show me the entry and the pull request text before you send anything. If I also want to submit the app for the
maintainer's collection, prepare that submission as well (same step) and show it to me first.
```

## 1. Role and goal (agent, read this first)

You are the lead developer of a **port** of Neolume – an unofficial client for Plex Media Server – to the human's TV.
Goal: an app on that TV with the **same functions and look** as the reference app, adapted to the TV's control concept and
using the TV's advantages, that meets the reference's acceptance criteria and performance budgets.

**Guiding principle:** build the **best possible version of the app for this TV** – not a minimal copy of the 2014
reference. Wherever there are several ways (reuse or rewrite, player API, rendering approach, image sizes, effects,
codecs), choose the one that gives the best result on this TV in quality, speed, smoothness and reliability – measured,
and agreed with the human. The spec defines the behaviour and the minimums, never a ceiling (section 1.3 for reuse,
section 7 for the headroom of a faster TV).

Your sources of truth, in this order:

1. **The product specification** – [SPEC.md](SPEC.md). Every requirement has an ID (`NAV-5`, `PLAY-3` …), some have
   explicit *Accept:* criteria; numbers are marked measured [M] or target [T]; [?] marks unverified points – verify them
   on the target. Part B lists the old TV's workarounds and their modern replacements; Part C is the porting guide and the
   API contracts. Always refer to requirements **by ID** (in code comments, tests, commits and `REQUIREMENTS.md`).
2. **The acceptance test plan** – [TEST-PLAN.md](TEST-PLAN.md): one entry for every Part A requirement, either a test you
   walk the human through (written so you can read it out step by step) or a check you do yourself. It decides whether a
   feature is done.
3. **The design system** – `design/tokens.json` (every colour, type style, spacing, radius, focus, motion and layout value,
   each with a description and how it scales to 1080p/4K) and the icon SVGs in `design/icons/`. Take values from these
   files – never measure colours or sizes from screenshots.
4. **The reference screenshots** and the **visual-test scene list** – how each screen looks, and the list of screen states
   that must exist in the port.
5. **The UI text tables** – `src/i18n/strings.en.js` and `src/i18n/strings.de.js`. Reuse the texts as they are (same terms
   and button names, SPEC A15); the length limit of each key prefix is in `tools/i18n_rules.js`.
6. **The reference source code** – the reference repository (ES5 web app; pure logic modules in `src/core`, `src/plex`,
   `src/player` with Node unit tests in `tests/`). Read it when the spec is not precise enough; the code wins over your
   assumptions, the spec wins over the code's 2014-specific workarounds. Section 1.2 lists the parts you can reuse.

All of these are maintained together with the app and checked on every build of the reference, so they are current as long
as you read them from the `main` branch. **Re-read the relevant SPEC sections and test-plan entries at the start of every
phase** – they change with each release (version above).

### 1.2 Reusable parts of the reference implementation

Much of the reference is **platform-independent logic**: no DOM, no network calls of its own, unit-tested in Node. On a
web-based TV platform (Tizen, webOS, a WebView or any browser engine) you do not even have to pick modules: you take over
the **whole reference app** and replace only the parts bound to the 2014 TV with a platform adapter (section 1.3). On a
native platform (Kotlin, Swift) port these modules line by line **together with their unit tests** – the tests are the
quickest proof that your port behaves the same. Every module is an ES5 function that attaches itself to one global namespace `N` (`N.util`,
`N.t` …). When you copy one, replace that with your module system and swap the dependencies the generated table names.

### 1.3 Reuse the reference app or rewrite it (decide in phase 0)

The reference is a complete web app (HTML, CSS, ES5 JavaScript). Choose one of two routes in phase 0, write it with its
reason into `PLATFORM.md` and the state file, and tell the human. Reuse is a means, not a goal: after the phase 1 spike,
decide **per area** (views and navigation, player, network, storage …) whether taking over the reference code is really
the better way, and note each decision with a short reason in `PORTING-STATE.md`. Rewrite a part when the engine has quirks
the reference does not expect, when the platform's player API is too different for a clean adapter, or when measurements
show a native version is clearly faster. Mixing is fine – for example, reuse the logic and the views and write the player
natively.

- **Web route – take over the reference app.** For TVs that run web apps: Samsung Tizen (2015 and later), LG webOS,
  Android TV / Google TV / Fire TV with a small native shell that shows the app in a full-screen WebView (or a
  browser-based shell), and other TV platforms with an HTML5 app runtime. Take `src/` largely **as it is** – screens,
  navigation and focus rules, player flow, texts, styles – and write a thin **platform adapter** that replaces only the
  parts bound to the 2014 Samsung TV (table below). Keep the build (`tools/build.js`), the unit tests in `tests/` and the
  visual-test harness (`tools/visual.js`); they keep working because the adapter sits outside the logic. This is much
  less work than a rewrite and keeps the behaviour identical to the reference; use the faster TV afterwards (1080p,
  native player features, section 7) step by step.
- **Native route – follow the spec.** For TVs that run only native apps (Apple TV / tvOS), or a native Android TV app if
  the human prefers one or the WebView turns out too slow: build the UI natively from the spec and reuse what is not tied
  to the web – the pure logic modules of section 1.2 (translated together with their tests), the texts, the design
  tokens and icons, the test data in `tests/synthetic/` and the test plan.
- **Not sure** (typically Android TV: WebView or native)? Decide with numbers: in the phase 1 spike run the reference app
  in the WebView with the first adapter and run the benchmark (SPEC A17.3). If the budgets of SPEC A17.1 hold, stay on
  the web route.

## 2. Ground rules

- **Ask the human only** for physical actions (switching on developer mode, pressing remote buttons, confirming what the
  TV shows, connecting cables), for consents (installing tools, changing TV settings, publishing) and for preferences.
  Find everything else out yourself (documentation, experiments, logs).
- **Never ask for or accept passwords, Plex tokens or PINs in the chat.** Sign-in happens on plex.tv in a browser or on the
  TV (SPEC A4, SEC-2, SEC-3). Tokens never go into logs, commits or messages. If a secret appears anywhere, tell the human
  to revoke it on plex.tv (*Authorized Devices*).
- **Local values** (TV and server addresses, developer certificates, keys) go into a git-ignored config file; add the
  `.gitignore` entry before the first commit.
- **Never** factory-reset the TV, change router settings, disable security features beyond the TV's official developer
  mode, or scan networks other than the human's own (and only with consent).
- **State file:** keep `PORTING-STATE.md` in the port repository: the spec version you build against (version line
  above), current phase, done/open requirement IDs, decisions with reasons, open questions for the human, measured
  numbers. Update it at the end of every work step so a new session can continue from it. Keep `REQUIREMENTS.md`: every requirement ID of SPEC.md with status (`done`, `partial`, `planned`,
  `n/a` + reason) and how it was verified.
- **Commit often** (small commits, message names the requirement IDs). Work in the phases below; a phase is finished only
  when its **exit criteria** are met and recorded in the state file.
- **See it yourself.** Check every visible change on the real TV with your own screenshot or camera picture (section 6,
  step 3) before you report it as done, and say what you looked at. If you can only rely on the human's description, say
  so in your report – it is a weaker check.
- **Don't invent behaviour.** If SPEC.md and the reference disagree or something is unclear, note it in the state file,
  choose the reference behaviour, and tell the human.
- **Brand and policy:** no "Plex" in the app name or icon, no impersonation of official apps, no telemetry (SPEC A18). Use
  your own app name; keep the notice "unofficial client for Plex Media Server, not affiliated with Plex, Inc.".

## 3. Phase 0 – discover the target platform

Find out, by research and by asking the human to read things off the TV, and write the results to `PLATFORM.md`:

1. Exact model, OS name and version (the human reads it from the TV's About/Support page).
2. The official developer program and SDK/CLI for this OS; how to enable developer mode on this model; licence/account
   requirements; how long a developer install stays valid.
3. How apps are installed: store, sideloading, developer install; packaging format and signing.
4. Logging and debugging channels from the TV back to the computer (debugger, log stream, network log endpoint).
5. Remote key injection from the computer (needed for automated tests and the benchmark); if none exists, plan an in-app
   benchmark that presses keys itself (SPEC A17.3).
6. Runtime capabilities: UI resolution and density, app technology options (web, native), video/audio codecs and HDR
   formats the player decodes (to be confirmed at runtime in phase 1), subtitle rendering, TLS 1.2+ to plex.tv
   (→ decide: sign-in on the TV and direct plex.tv calls, **no helper** – SPEC B-1, C1), input devices (D-pad, colour keys,
   digits, pointer, touch surface, voice), background/screensaver APIs, secure storage.
7. If there is **no supported way** to install own apps: stop and tell the human; suggest an Android TV / Google TV device on
   the HDMI input instead and continue with that platform.
8. **Reuse or rewrite** (section 1.3): web route (take over the reference app with a platform adapter) or native route
   (rewrite from the spec, reuse the pure logic, texts, tests and assets) – with the reason.
9. **How you see the screen.** Arrange it now, not when the first bug appears – you will check every visible change
   yourself (section 6). In this order:
   - the platform's **screenshot command**, run by you: e.g. `adb exec-out screencap -p > shot.png` on Android TV,
     Google TV and Fire TV; on other platforms look for a capture function in the SDK or the developer tools and try it.
     Screenshots often leave out the video layer (black picture) or are blocked during protected playback – plan the
     camera for player checks then;
   - otherwise a **camera pointed at the TV** that you can read frames from yourself: a webcam on the computer (e.g. one
     frame with `ffmpeg`), a phone with an IP-camera app, or a network camera (snapshot URL or video stream). Ask the human
     to put it on a stand facing the whole screen, and check one frame together;
   - otherwise the **human describes** what they see. Tell the human plainly that this is much slower and that small
     mistakes will slip through, and offer the two options above again.

**Exit criteria:** `PLATFORM.md` answers all nine points with sources (links) or "verified on the TV"; the technology
choice, the route (web or native) with its reason, the way you see the screen and the install channel are agreed with the
human.

## 4. Phase 1 – connectivity spike

Build a first app and get it running on the TV – on the web route this is already the reference app with the first
version of the platform adapter (start, keys, storage; the player and plex.tv may still be missing), on the native route a
throw-away "hello" app:

- installed and launched from the computer with one command (document it in the README),
- shows resolution, OS/engine version and every key press with its key code (to map the control concept, SPEC A3, C1),
- sends log lines to the computer (or a readable on-device log),
- receives injected key presses from the computer (or runs a self-driving key sequence),
- makes one plain request to the human's Plex Media Server (`GET /identity`, no token – SPEC C2.1) and shows the result,
- measures the **direct-play matrix**: which formats the device's own player plays without the server converting them.
  Use short test files from the human's library (the human picks titles; you play them directly, without transcoding)
  and the platform's capability APIs: containers (MKV, MP4, TS …), video codecs (H.264, HEVC, VP9, AV1) with bit depth,
  maximum resolution, frame rate and bitrate, HDR10 / HLG / Dolby Vision, audio codecs and passthrough to the AV
  receiver or soundbar (AC3, E-AC3/Atmos, DTS, TrueHD), and the subtitle formats the player draws itself (SRT, ASS/SSA,
  PGS). Record it in `PLATFORM.md`; it becomes the client profile of PLAY-3, so the server converts only what the TV
  really cannot play,
- is visible to you: you take a screenshot or camera picture of the running app yourself, look at it and describe it
  correctly to the human (web route: also check that answers of the Plex Media Server arrive despite CORS, section 1.3).

**Exit criteria:** all seven items demonstrated on the TV; the key map, the codec list and the screen-capture command are
in `PLATFORM.md`.

## 6. Verification loop (after every change that matters, and at every exit)

1. **Unit tests** for the pure logic, ported from the reference tests where possible: start rules PROF-2, decision and
   fallbacks PLAY-3 … PLAY-5, versions PLAY-6, track choice PLAY-9, markers and up next PLAY-17 … PLAY-18, seeking PLAY-22,
   home-row merge HOME-4, library queries LIB-3. Use synthetic data like the reference's `tests/synthetic`.
2. **Visual parity:** render the same states as the reference scenes/screenshots and compare layout, proportions, colours,
   focus styles and texts (scaled per [SPEC A16.6](SPEC.md#a166-scaling-to-1080p-and-4k)). List differences in the state
   file and fix them or justify them (control concept, platform convention). How, with the tools of section 1.4:
   - **Web route:** run the reference tools directly on your port. Keep the build output (`app/app.min.js` from
     `tools/build.js`) and the desktop adapter `tools/preview.html` working next to your platform adapter; then
     `tools/visual.js` renders your own code in every scene, the layout check inspects it, and `tools/bench.js` measures
     it. Approve the reference's pictures once before you change anything (a clean checkout, a full run,
     `npm run visual:approve`); from then on every red `diff-*.png` is a difference you either fix or justify. New
     scenes for platform-specific screens go into the `SCENES` list too.
   - **Native route:** the tools cannot drive a native app. Render the reference states with `tools/visual.js`
     (`--only` with the scenes of the screen you are building), take screenshots of your port in the same state, and
     compare them side by side; the scene list is your checklist. Port the layout check's rules where your UI toolkit
     allows (no overlapping or cut-off text, nothing in the title-safe margin), and implement the benchmark scenarios
     natively (point 4).
3. **Look at the TV yourself:** after every visible change, take a screenshot or camera picture of the affected screen on
   the real TV (phase 0, point 9) and compare it with the reference screenshot and the spec **before** you report the
   change as done; name in your report what you checked. Camera pictures: same position and light each time, cropped to
   the screen; their colours are approximate – take colour values from the tokens and use the picture for layout, text,
   focus and motion. Keep the pictures out of the repository (git-ignored folder) and delete them when the phase is done:
   they may show the room.
4. **Performance:** implement the benchmark scenarios of [SPEC A17.3](SPEC.md#a173-measuring) (same key sequences,
   160 ms rhythm, same metrics) and compare with the budgets PERF-1 … PERF-13; record the numbers in the state file. On fast
   hardware tighten the budgets (60 fps, no frame over 33 ms), never loosen them. Web route: the scenarios come with the
   reference code – start them on the TV with the digit sequences of A17.3 and use `tools/bench.js` on the computer for
   quick before/after comparisons; only the TV numbers count against the budgets.
5. **On-device checks with the human** for what you can't check yourself: look and feel from the sofa, pointer/touch behaviour,
   picture and sound in the player matrix. Take the steps from [TEST-PLAN.md](TEST-PLAN.md) (the entries of the
   requirements you just built, plus the 10-minute smoke test of its section 2 after every fix), translate the key names
   with the key map in `PLATFORM.md`, and record the answers. **Whenever you are unsure mid-way** whether something behaves
   as specified, run the matching test-plan entry with the human instead of guessing.

## 7. Adaptation rules

- **Control concept:** map the reference keys (SPEC A3.2, A3.3) to the platform's remote. Every colour-key and digit
  function must stay reachable without those keys (NAV-1): buttons, the context menu (long press), the hint bar. Pointer
  remotes: implement NAV-2 including the damping rules of Part B (B-8). Use the platform's Back key for RETURN.
- **Platform advantages:** UI at 1080p/4K (SPEC A16.6); codec support from runtime capabilities in the client profile
  (PLAY-3, B-7); native text/ASS subtitle rendering (PLAY-11); request headers instead of tokens in URLs (SEC-3); secure
  storage for tokens; direct plex.tv sign-in and Discover/watchlist (B-1 – no setup program, no helper); voice/system search
  feeding Search (SRCH-1) where offered; gapless audio and playback speed where the player offers them (MUS-8): one scale from −32× through 1× to 32×,
  pitch-preserving tempo with sound around 1× (0.5× … 2×, 2.5×/3× only if speech stays clear), silent trick play beyond
  and backwards, video speed per playback session, audiobook speed remembered per book (PLAY-33; the 2014 reference only
  has the silent part, PLAY-32).
- **Use the headroom of a faster TV:** the performance numbers in the spec (PERF-*) are minimums for a 2014 TV, not
  limits. Whichever route you took (section 1.3), test on the device whether it can deliver **better versions** of the
  features you built, and adopt each improvement with the human's OK. Measure the device first (an animation and
  list-scrolling test in the probe app), then look at:
  - *shorter load times:* bigger caches, prefetching the next row or page, more requests in parallel where the budget
    allows (NET-3 caps them for the 2014 TV);
  - *sharper display:* a native 1080p/4K UI instead of the scaled 720p one, larger transcode and thumbnail sizes, 1080p/4K
    backgrounds (SPEC A16.6), and the generated images (`tools/make_assets.js` draws icon sprite, scrims and fades from
    code and `design/icons/` – render them at 2× or 3×);
  - *smoother effects:* slightly longer transitions, effects the 2014 engine could not do (real blur, shadows,
    gradients);
  - *above all, direct play:* feed the measured direct-play matrix of phase 1 into the client profile (PLAY-3, B-7), so
    HEVC, HDR, AV1 or surround sound play directly and the server converts only when really needed.

  Keep the "no work in the focus step" rules anyway – they make every device feel faster. Record each upgrade in the
  state file with a measurement before and after (load time, fps, image size, number of transcodes in the player matrix).
- **Other control concepts:** a different remote changes more than key codes. D-pad only (no pointer, e.g. Android TV,
  tvOS): every pointer feature needs a key path or is left out on purpose – e.g. fine scrubbing (PLAY-30) is pointer-only,
  the key path is the accumulated seeking of PLAY-22; hover previews become focus previews. Air-mouse pointers (LG Magic
  Remote) or touch surfaces other than the 2014 Smart Touch: do not copy the damping values of Part B (B-8) – tune dwell
  times, jitter and edge zones with the human on the real remote and record them. Touch screens, gamepads or voice:
  ask the human which ones matter and test each with them.
- **Drop the 2014 workarounds** listed in Part B (B-1 … B-18) unless `PLATFORM.md` shows the same limitation on this TV;
  record each decision in the state file.
- **Keep the product rules:** cache-first start, per-profile settings, the "no work in the focus step" rules PERF-14 …
  PERF-16, texts within the limits of SPEC A15, PMS-only daily use (PRIN-12).

## 8. Finishing

1. **Release packaging** for the agreed install channel; one-command install documented in the README; release checksums.
2. **Walk the human through [TEST-PLAN.md](TEST-PLAN.md)** – the final acceptance test. Install the release build, go
   through its device setup checklist, the smoke test, every test of section 3 (one area at a time; it can be spread over
   several sessions), the performance measurements with your benchmark (section 4) and the privacy and security checks
   (section 5). Do all agent checks yourself first. Collect the answers in the results template (section 6), copy them into
   `REQUIREMENTS.md`, fix every failure and repeat that test plus the smoke test. The port is done when every applicable
   test passes; list the rest as known gaps.
3. **Privacy and security checklist:** SEC-1 … SEC-8 (no telemetry, no tokens in logs/URLs where avoidable, home-network
   rules, kids safety, diagnostics only on request) – verified through section 5 of the test plan; note each result in
   `REQUIREMENTS.md`.
4. **Texts:** friendly, correct, explain what and why; same terms as the reference (TXT-2, TXT-3).
5. **README** for end users: what it is, the trademark notice, install steps for this TV, how to sign in, known gaps
   (from `REQUIREMENTS.md`).
6. **Register the port** (only with the human's consent): a pull request to the reference repository adding one entry to
   `ports.json` (format `ports.schema.json`, `specVersion` = the version at the top of SPEC.md, `features` per Part A
   section from `REQUIREMENTS.md`), or the *Port submission* issue form. Policy: [community ports](../PORTS.md).
   Optionally, the human may also **submit the finished app for the maintainer's collection** (*Collection submission*
   form; what to send and how it is reviewed: "Submit your app for the collection" in [PORTS.md](../PORTS.md)) – only
   with public source code, the test-plan results and an install guide for that TV. Prepare it, show it to the human,
   and send nothing without their OK.

## 9. Staying current

When the reference publishes a new version (version line above), diff the maintained sources in a clone of the reference
(`git diff <old tag> <new tag> -- docs/SPEC.md docs/TEST-PLAN.md design/ src/i18n/` – section 1.1 lists them), implement

and `lastVerified` of the port's entry in `ports.json`.

## 10. Using another media server (Jellyfin/Emby)

The reference app is a client for Plex Media Server. If the human runs **Jellyfin** or **Emby** instead, the same app can
be built for that server: the screens, navigation, player flow, texts, design and most of the logic stay; only the layer
that talks to the server is replaced. This is **not part of the reference** and has not been tested by its maintainer –
treat it as an extra phase with its own decisions, and agree on it with the human in phase 0.

**Order.** Build the Plex version first as far as phase 1 (or the whole app, if the human also has a Plex server):
the reference's mock server and test data speak Plex, so the visual tests and the benchmark keep working while you
write the adapter. Then add the server adapter and test it against the human's real server and against your own
synthetic answers.

**How.** Everything the views need from the server goes through the Plex client layer: `N.plex` in `src/plex/client.js`
(requests, identification headers, URL building, image URLs, the one write function) and the modules built on it in
`src/plex/` (Home rows in `hubs.js`, library queries in `library.js`, details in `details.js`, search in `search.js`,
music in `music.js`), plus the player's server calls in `src/player/decision.js` (decision, playback URL),
`src/player/playback.js` (timeline) and `src/player/thumbs.js` (scrubbing previews). `src/plex/model.js` turns server
answers into the small objects the views use.

1. List every call the app makes through `N.plex` (search the code for `N.plex.` and `P.get`-style calls) and group them
   by screen. This list is the interface of your **server adapter**.
2. Write the adapter for the target server with the **same functions and the same result objects** as the Plex layer –
   map the server's answers in your own `model` step to the objects `src/plex/model.js` produces (card kinds, badges,
   progress, sub-lines). Then the views, Home rows and the player flow do not change.
3. Keep the request rules of NET-3 (`src/net/http.js`): timeouts, retries, at most 3 parallel requests where the TV is slow.
4. Write synthetic answers of the target server in the style of `tests/synthetic/` and port the unit tests of the
   modules you changed. Read the API description that the server itself publishes (Jellyfin serves an OpenAPI
   document; Emby documents its REST API) for the **server version the human runs** – route names changed between
   versions, so check each one in the phase 1 spike with a plain request.
5. Record the server name and version in `PLATFORM.md`, and every mapping decision in `PORTING-STATE.md`.

**Concept mapping.** Names are Jellyfin's; Emby's API is very similar (it shares the origin), usually under the prefix
`/emby/`. Verify each route against the human's server version before you rely on it.

| What the app needs | Plex (reference) | Jellyfin / Emby | Notes |

- plex.tv **Discover**, inspiration rows and the **watchlist** (SPEC A8.2, A8.3; DISC-1, DISC-2, DISC-3, DISC-4, DISC-5) – they
  come from plex.tv, not from the media server. Search stays (A8.1).
- **Other servers shared with you** through plex.tv (SPEC A11; SRV-1, SRV-2, SRV-3, SRV-4). An "add another server by its

- The **setup program, `setup.json` and the helper** (PROF-1, C2.2, C2.3, C2.4) – a TV that can reach its home server

- Plex Home **profile switching with a Plex PIN** and plex.tv **sign-out/account change** (PROF-10, A4.5) – replaced by
  "switch user" and "sign out of this server" on the TV.
- **Anime detection** (PLAY-15) uses Plex metadata; map it to the server's genres and provider ids, or mark it partial.

**Texts and branding.** Reuse the string tables and replace "Plex" in the texts that name the server (sign-in, server
errors, settings) with the server's name – same length limits (`tools/i18n_rules.js`). The app name must not contain
"Plex", "Jellyfin" or "Emby", and must not use their logos; describe it as "an unofficial client for Jellyfin" (or Emby).

**Testing.** The acceptance test plan ([TEST-PLAN.md](TEST-PLAN.md)) applies as written, with the server's words:
"visible in other Plex apps" means "visible in the server's web app and other apps of that server". Record which tests
are `n/a` and why.

maintainer's collection and might later be offered there as its own download.
